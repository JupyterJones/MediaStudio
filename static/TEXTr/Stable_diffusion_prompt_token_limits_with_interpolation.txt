## Why you don't see a warning

SD1.5's text encoder is CLIP ViT-L/14, and its tokenizer has a hard `model_max_length` of 77. That's 75 actual text tokens plus a `<|startoftext|>` and `<|endoftext|>` token bookending them.

When you call the tokenizer with a prompt longer than that, the standard behavior (in `transformers`/`diffusers`) is:

```python
text_inputs = tokenizer(
    prompt,
    padding="max_length",
    max_length=tokenizer.model_max_length,  # 77
    truncation=True,
    return_tensors="pt",
)
```

`truncation=True` means it just chops off everything past token 77 — no exception, no error. Diffusers *does* try to warn you about this: internally it decodes the untruncated version and compares it to the truncated one, and if they differ it calls `logger.warning(...)` telling you what got cut off. But that's a call into Python's standard `logging` module, not a `print()` or an exception. If you (or your serving layer) haven't called `logging.basicConfig()` to attach a handler, or if the root logger's level is above `WARNING`, that message just gets swallowed — it fires, but nothing renders it anywhere you'd see. That's almost certainly what's happening in your setup, especially if you're doing custom lower-level model loading rather than going through the full diffusers pipeline (which sets up its own logger).

You can check this yourself without depending on the warning at all:

```python
tokens = tokenizer(prompt, truncation=False)["input_ids"]
print(len(tokens))  # if > 77, it's getting silently cut
```

## How this actually affects interpolation

This matters differently depending on which kind of interpolation you're doing:

**Latent interpolation** (slerp between two noise latents / intermediate denoising states) — not affected at all by prompt length. That's happening in latent space; the text conditioning is just held fixed (or also interpolated separately, see below). Truncation only touches the text→embedding step.

**Prompt/embedding interpolation** (encoding prompt A and prompt B separately, then slerp/lerp between their embeddings before cross-attention) — this is where it gets subtle. Each prompt is tokenized and truncated to 77 tokens *independently*, so you get two tensors both shaped `[77, 768]` (for SD1.5's CLIP). The interpolation then happens position-by-position across those two `[77, 768]` tensors. Two things to watch for:

1. If prompt A is 40 tokens and prompt B is 90 tokens, prompt B silently loses its tail — so you might think you're interpolating toward some detail at the end of prompt B and it's just not in the embedding at all.
2. Position-wise interpolation assumes token position *i* in prompt A is roughly comparable to token position *i* in prompt B. CLIP's text embeddings are contextualized (each position's vector is influenced by the whole sequence via self-attention), so this works better than you'd expect even when the underlying words don't line up — but it's still a soft blend of contextual features, not a semantic word-to-word morph. Wildly different prompt lengths/structures between A and B tend to produce mushier interpolation midpoints for this reason.

## Practical takeaway for your workflow

Since you're doing custom serving rather than going through a full pipeline wrapper, I'd suggest two things:

1. Explicitly check token length before encoding (the snippet above) so you know when truncation is happening instead of finding out via weird results.
2. If you want prompts longer than 75 tokens for interpolation, the common trick (used in A1111's prompt weighting extensions) is chunking: split the prompt into 75-token chunks, encode each chunk separately (each still gets its own BOS/EOS), then concatenate or average the resulting embeddings before interpolating. It's more code, but it's the only way to actually use the full prompt content rather than silently losing text.

## The 77 limit isn't a CLIP-model limit, it's a *tokenizer/positional-embedding* limit

CLIP's text encoder has a positional embedding table with exactly 77 rows — one per sequence position, up to `model_max_length`. That table is baked into the model weights; you can't feed it a 150-token sequence in one pass and expect anything sane out.

But the **U-Net's cross-attention layers don't care how long the text sequence is.** Cross-attention just does `softmax(Q @ K.T) @ V` where Q comes from the image latent and K/V come from your text embedding sequence. K and V can be length 77, 154, 231 — whatever. The U-Net has no positional assumption about the text side at all.

So the trick (this is literally what A1111's "long prompt weighting" and most "77 token bypass" implementations do):

1. Split your prompt into chunks of ≤75 tokens
2. Encode **each chunk separately** through CLIP (each gets its own BOS/EOS, each is a valid 77-length input to CLIP)
3. **Concatenate the resulting embedding tensors along the sequence dimension** — not average, not truncate, actually concatenate
4. Feed that longer concatenated tensor to the U-Net via `prompt_embeds=` instead of `prompt=`

That's the "send embeddings instead of text" you're describing — and yes, it genuinely lets you exceed 77 tokens, because you're bypassing the tokenizer's hard cap entirely and only ever giving CLIP itself valid 77-length chunks.

## Minimal version with diffusers

```python
import torch

def encode_long_prompt(pipe, prompt: str, chunk_size: int = 75):
    tokenizer = pipe.tokenizer
    text_encoder = pipe.text_encoder

    # tokenize with no truncation to see the full thing
    tokens = tokenizer(prompt, truncation=False, add_special_tokens=False)["input_ids"]

    chunks = [tokens[i:i+chunk_size] for i in range(0, len(tokens), chunk_size)]

    bos, eos = tokenizer.bos_token_id, tokenizer.eos_token_id
    embeds = []
    for chunk in chunks:
        ids = [bos] + chunk + [eos]
        ids += [eos] * (tokenizer.model_max_length - len(ids))  # pad to 77
        ids_tensor = torch.tensor([ids])
        with torch.no_grad():
            emb = text_encoder(ids_tensor)[0]  # [1, 77, 768]
        embeds.append(emb)

    return torch.cat(embeds, dim=1)  # [1, 77*n_chunks, 768]
```

Then instead of:
```python
pipe(prompt=prompt, ...)
```
you do:
```python
embeds = encode_long_prompt(pipe, prompt)
pipe(prompt_embeds=embeds, ...)
```

`diffusers` pipelines accept `prompt_embeds` directly for exactly this reason — it's a documented escape hatch from the tokenizer path.

## What this means for your interpolation case specifically

Two different situations, worth distinguishing since your last example had identical text on both sides:

**If you interpolate between two *different* long prompts:** chunk both the same way (same `chunk_size`), pad both to the same number of chunks (pad the shorter one with empty/EOS-only chunks so shapes match), then slerp/lerp the resulting `[1, 77*n, 768]` tensors position-by-position, same as you would with a 77-length embedding. The concatenation doesn't change the interpolation math, just gives it more positions to work over.

**If you're doing weight scheduling on one prompt** (which is what your `.36`/`.64` log actually looked like) — this chunking trick is unrelated to that; you'd apply your weight scaling to the concatenated embedding the same way you were applying it before.

## The CPU/16GB angle, since this is your actual hardware

Cross-attention cost scales roughly with sequence length for the K/V side, so going from 77→154 tokens roughly doubles that portion of attention compute per step — noticeable on CPU, but not brutal, since attention isn't the dominant cost in SD1.5's U-Net (the conv blocks are). Memory-wise, an extra 77×768 float tensor is trivial (~230KB), so this is a compute-time tradeoff, not a memory one. Given you're already running LCM for speed, going to 2-3 chunks (150-225 tokens) is very affordable; I wouldn't go past 3-4 chunks on CPU-only without expecting per-frame time to climb noticeably, especially across a 249-frame interpolation run like your log showed.
